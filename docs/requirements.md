# 单向隔离网络 MySQL 数据同步系统需求说明

## 1. 项目背景

现有业务需要将源 MySQL 数据库中的指定表数据，同步到隔离网络中的另一套 MySQL 数据库。

现有网络链路如下：

源 MySQL
→ 源端同步程序
→ HTTP 文件上传接口
→ 中转服务器
→ FTP 服务
→ 隔离网络内 FTP 客户端
→ 目的服务器
→ 目标 MySQL

网络为严格单向链路。

隔离网络中的程序只能从 FTP 服务端获取文件，不能向源端或中转端返回同步结果、ACK、状态信息或其他数据。

源端只能确认文件是否已经通过 HTTP 接口可靠上传到中转服务器，无法直接知道目标数据库是否已经完成同步。

---

## 2. 当前环境和限制

### 2.1 源数据库

源数据库为 MySQL。

当前已知：

* MySQL 5.7.35
* 开启 Binlog
* `binlog_format=ROW`
* `binlog_row_image=FULL`
* GTID 已开启

但由于权限限制，当前同步程序不能读取 Binlog，因此 V1 不依赖 Binlog CDC。

源业务表不能修改，包括：

* 不增加字段；
* 不修改主键；
* 不增加同步字段；
* 不依赖 Trigger 修改业务表行为。

允许同步程序在自己的环境中建立状态库、状态表或其他辅助数据。

### 2.2 源服务器

源端运行在 Windows Server。

可用磁盘空间约 200GB，因此：

* 不能长期保存大量历史同步文件；
* 不能要求一次生成完整的超大同步包后再上传；
* 同步文件应支持边生成、边上传、成功后释放本地空间。

### 2.3 数据特点

需要同步的表数据量差异较大，部分表可能达到 700 万行以上。

源数据存在以下情况：

* 部分表有数据库主键；
* 部分表没有数据库主键；
* 部分表可能存在可作为逻辑唯一键的字段；
* 部分表可能不存在可靠唯一键；
* 更新时间字段不可靠；
* 历史旧数据可能被修改；
* 上游系统可能一次性更新大量数据，极端情况下可能一次改变数百万行。

因此不能仅使用：

* 最大 ID；
* 更新时间；
* 创建时间；

等方式判断增量数据。

---

# 3. 建设目标

系统需要实现：

1. 将指定源 MySQL 表可靠同步到隔离网络中的目标 MySQL。
2. 第一次同步支持全量数据。
3. 后续同步尽量只传输实际发生变化的数据。
4. 不依赖源表更新时间。
5. 支持历史数据修改。
6. 支持新增、修改、删除数据。
7. 支持没有数据库主键的表。
8. 支持单次出现数百万行变化的情况。
9. 大量变化必须拆分传输，不能形成一个超大文件或一个超大数据库事务。
10. 支持程序中断后的恢复。
11. 目标端能够自行验证最终数据是否与源端一致。
12. 数据不一致时提供简单的人工修复方式。

系统不要求实现源端和目标端的实时强一致。

目标是一套：

**可靠的最终一致性数据同步系统。**

---

# 4. V1 同步方案

## 4.1 正常同步方式

由于当前无法读取源数据库 Binlog，V1 使用：

**源表扫描 + 本地状态比较 + 增量文件传输**

基本过程：

源 MySQL
→ 流式扫描指定表
→ 与上一次同步状态进行比较
→ 找出新增 / 修改 / 删除数据
→ 生成增量数据文件
→ HTTP 上传
→ FTP 单向传输
→ 目标端写入 MySQL

需要明确：

**源数据库每次可能仍需要扫描整张表，但网络只传输发生变化的数据。**

例如某表共有：

7,000,000 行

本次实际变化：

* 新增 500 行；
* 修改 3,000 行；
* 删除 200 行。

则源端可以读取整张表进行比较，但最终只需要生成约 3,700 条变化数据。

---

# 5. 数据变化识别

同步程序需要针对不同表支持不同的数据识别方式。

## 5.1 有可靠唯一键的表

优先使用：

* 数据库主键；
* 或经过验证的逻辑唯一键。

同步程序保存：

唯一键 + 当前数据指纹

下一次扫描时进行比较。

根据比较结果识别：

* INSERT；
* UPDATE；
* DELETE；
* 未变化。

## 5.2 没有数据库主键的表

如果存在稳定且唯一的业务字段组合，可以配置为逻辑唯一键。

是否能够作为逻辑唯一键必须根据实际数据验证，不能只根据字段名称判断。

## 5.3 完全没有可靠唯一键的表

必须仍然能够同步。

可以通过完整行数据指纹及重复数量等方式识别数据集合变化。

具体算法属于开发设计内容，不在本需求中固定。

---

# 6. 本地同步状态

源端需要保存上一轮已经确认生成完成的数据状态，用于下一次比较。

状态数据主要用于记录：

* 表；
* 数据唯一标识或行指纹；
* 数据内容指纹；
* 最近同步版本；
* 同步任务状态。

原则上不要求在本地保存一份完整业务数据库副本。

本地状态应尽量只保存同步所需的数据，以减少 200GB 磁盘空间的使用。

---

# 7. Run 和 Chunk

系统需要区分：

## 7.1 Run

一次完整的表扫描产生一个同步版本，称为 Run。

例如：

`table_A / Run 10023`

代表源端完成了一次该表的状态检查。

## 7.2 Chunk

一个 Run 中的数据需要拆分成多个小文件，即 Chunk。

例如一次发现：

7,000,000 条变化

不能生成一个包含 700 万条数据的文件。

需要拆分为：

* Chunk 000001
* Chunk 000002
* Chunk 000003
* ...

Chunk 大小由程序根据：

* 行数；
* 文件大小；

进行限制。

具体数值在性能测试后确定。

---

# 8. 大批量变化处理

如果某张表一次发生数百万行甚至全表变化：

1. 系统不能一次全部加载到内存。
2. 系统不能一次形成一个超大文件。
3. 系统不能一次使用一个超大 MySQL 事务写入目标库。
4. 数据必须分 Chunk 生成。
5. Chunk 可以逐个上传。
6. HTTP 上传确认成功后，源端允许删除已经上传的本地 Chunk。
7. 后续 Chunk 继续生成和上传。
8. 目标端同样需要将一个 Chunk 拆成较小的数据库写入批次。

因此即使一次变化 700 万行，也应作为一个较大的同步任务逐步完成，而不是一次性同步。

---

# 9. 源端磁盘控制

由于源 Windows Server 只有约 200GB 空间，同步程序必须限制自身磁盘占用。

要求：

* Chunk 生成后尽快上传；
* HTTP 服务确认文件可靠接收后，可以删除源端该 Chunk；
* 不长期保存已经成功上传的历史同步文件；
* 磁盘空间不足时暂停新的扫描或文件生成；
* 已经生成的文件优先上传和释放空间；
* 程序不得因为同步任务耗尽系统磁盘空间。

中转服务器已经能够在 HTTP 上传时完成：

* 临时文件写入；
* flush；
* 文件关闭；
* SHA256 校验；
* 原子 rename；
* 数据库登记；
* 成功响应。

因此源端收到该成功响应后，可认为：

**该文件已经可靠交给中转服务器。**

但不能认为目标数据库已经同步成功。

---

# 10. 单向网络处理原则

由于网络政策明确禁止任何反向信息：

目标端不能向：

* 中转服务器；
* 源服务器；

返回同步成功或失败状态。

因此系统不尝试实现网络层面的端到端 ACK。

责任边界定义如下：

### 源端

负责：

* 正确扫描源数据库；
* 正确生成变化数据；
* 正确生成校验信息；
* 将文件可靠交给 HTTP 中转服务器。

### 目标端

负责：

* 获取完整文件；
* 校验文件；
* 写入目标 MySQL；
* 自行验证同步后的数据是否正确。

---

# 11. 文件完整性

每一个同步文件必须包含或关联完整性信息。

至少需要：

* Run ID；
* Chunk 编号；
* 表名；
* 数据条数；
* 文件 SHA256。

目标端处理文件以前必须先验证文件完整性。

校验失败的文件不能写入数据库。

---

# 12. 目标端文件处理

FTP 客户端从中转服务器下载文件后，中转服务器上的文件可能被删除。

因此目标服务器必须首先将下载文件可靠保存到自己的磁盘。

文件不能在数据库处理完成以前删除。

建议至少区分：

* 待处理；
* 处理中；
* 已完成；
* 失败。

目标端程序中断或 MySQL 写入失败后，应能够使用本地文件重新执行。

---

# 13. 幂等处理

同步文件必须允许重复处理或重复出现，而不能造成数据重复。

目标端需要记录已经成功处理的：

* Run；
* Chunk；
* 文件校验值。

如果一个已经成功处理的 Chunk 再次出现：

程序应识别其已经执行成功，而不是再次重复写入数据。

---

# 14. 数据一致性验证

由于源端无法获得目标端反馈，数据一致性验证由目标端自行完成。

源端在每一次有效同步版本中，需要同时生成源数据的校验摘要。

校验信息随同步数据一起单向发送到目标端。

目标端完成数据库写入后：

1. 计算目标数据摘要；
2. 与源端发送过来的摘要比较；
3. 自动判断数据是否一致。

最终状态至少分为：

* `VERIFIED`：验证一致；
* `MISMATCH`：验证失败；
* `PROCESSING`：正在处理。

---

# 15. 分段校验

对于数百万行的大表，不要求只生成一个整表 Hash。

系统应采用能够定位错误范围的分段校验方式。

每个校验段至少包含：

* 数据数量；
* 数据摘要。

目标端使用相同规则计算。

如果全部匹配：

显示：

`VERIFIED`

如果部分不一致：

显示：

* 表名；
* Run ID；
* 不一致；
* 建议重新进行全量修复。

具体分段数量和 Hash 实现由开发阶段确定。

---

# 16. 人工操作要求

人工操作必须简单。

正常情况下：

**不需要人工操作。**

用户只需要在目标端看到：

`同步完成 / VERIFIED`

即可。

如果发生数据不一致：

目标端显示：

`同步失败 / MISMATCH`

并提示需要重新同步的表。

人工只需要通过现有允许的方式通知源端：

`重新同步 XXX 表`

源端提供简单操作，例如：

`生成全量修复包`

不要求操作人员：

* 手工编写 SQL；
* 手工寻找差异行；
* 人工计算 Hash；
* 人工比较大量数据。

---

# 17. 全量修复

系统需要支持针对单张表生成完整 Snapshot。

用于：

* 第一次同步；
* 数据校验失败；
* 同步状态损坏；
* 需要人工重新初始化某张表。

全量修复仍然必须：

* 分 Chunk；
* 支持大数据量；
* 不一次产生超大文件；
* 不一次使用超大数据库事务。

目标端完成全量同步后重新进行一致性验证。

验证通过后显示：

`VERIFIED`

---

# 18. 源数据继续变化时的处理

系统同步目标是数据最终状态，而不是保留源数据库中的每一次历史修改过程。

例如两次扫描之间一条数据发生：

100 → 200 → 300

系统允许最终只识别：

100 → 300

不要求同步中间的 200 状态。

---

# 19. 基本运行状态

源端至少需要能够查看：

* 当前正在扫描的表；
* 当前 Run；
* 已发现变化数量；
* 已生成 Chunk 数；
* 已成功上传 Chunk 数；
* 错误信息；
* 本地磁盘使用情况。

目标端至少需要能够查看：

* 表名；
* Run；
* 接收到的 Chunk；
* 当前处理状态；
* 成功/失败；
* 数据一致性验证结果。

界面或命令行形式由实现阶段确定，以简单易用为原则。

---

# 20. V1 不包含的内容

V1 暂不要求：

* Binlog CDC；
* 实时秒级同步；
* 双向数据同步；
* 目标端向源端自动返回 ACK；
* 分布式集群；
* 复杂消息队列；
* 自动跨网络反向修复请求；
* 保存数据库每一次历史修改记录；
* 修改现有源业务表结构；
* 为所有异常设计复杂自动恢复流程。

优先保证：

**简单、可靠、可维护。**

---

# 21. 验收标准

系统满足以下条件即可认为 V1 达到基本要求：

1. 能完成指定表第一次全量同步。
2. 后续能够识别源表新增、修改、删除数据。
3. 更新时间不可靠时仍不会因此漏同步。
4. 支持无数据库主键表。
5. 700 万行级别表能够流式处理，不要求整体加载内存。
6. 单次出现数百万条变化时能够拆分 Chunk 逐步传输。
7. 源服务器同步程序不会无限占用 200GB 磁盘空间。
8. HTTP 上传成功后可以安全释放源端对应文件。
9. FTP 下载后的文件在目标数据库处理成功以前不会丢失。
10. 文件损坏能够被发现。
11. 重复文件不会导致重复数据。
12. 目标端能够自动判断当前数据与源端校验结果是否一致。
13. 正常情况下无需人工参与。
14. 发生数据不一致时，人工只需要触发对应表的全量重新同步。
15. 全量修复完成后能够重新验证并得到 `VERIFIED` 结果。

---

## 22. 总体原则

本系统 V1 以满足当前实际业务需求为目标。

设计原则：

**能简单实现的，不增加复杂组件。**

**能自动完成的，不增加人工操作。**

**严格单向网络无法解决的问题，不通过复杂设计强行绕过。**

**通过源端可靠生成、文件可靠传输、目标端自动校验和简单人工全量修复，保证系统最终数据一致。**
